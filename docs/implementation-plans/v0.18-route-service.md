# v0.18: in-process serving through `route_service`

**Status:** in progress (2026-09-05)

## Goal

Let a test serve the app under test from inside the test process: an axum
`Router`, a tower-http `ServeDir` holding a built wasm bundle, or any tower
`Service`, wired to a URL pattern so the browser's requests are answered
without a socket. This is the one thing no other Playwright binding can
offer, because only here is the backend in-process Rust, and it is the
natural test harness for a Rust frontend with a Rust backend.

## Shape

- `Page::route_service(pattern, service)` and
  `BrowserContext::route_service(pattern, service)`, thin wrappers over
  `route` whose handler rebuilds each request as an `http::Request`,
  calls `tower::ServiceExt::oneshot` on a clone of the service, and
  fulfills the route with the response. Same mechanism as
  `route_from_har`: a source of responses wired into interception.
- Feature `route-service`, on by default. Adds `http`, `http-body`,
  `http-body-util`, and `tower` (util only) as optional dependencies, all
  already in the graph's audit set.
- `protocol::route_service` holds the two pure conversions (request from
  the driver's parts, fulfill options from an `http::Response`) under
  unit and mutation tests, plus the async fulfiller, plus the deep-dive
  rustdoc that is the feature's documentation: where it fits, what the
  service sees, what it is not, and how to wait on a wasm frontend.

## Decisions

- **Default-on.** In-process serving is the capability this crate can
  offer that no other binding can, and its cost is four small pure-Rust
  crates that were already in the audit set, so it belongs in the default
  experience. A second reason is a CI gap: nextest runs with default
  features only, which already leaves the `screenshot-diff` integration
  tests unexercised. Running the test jobs with `--all-features` closes
  that gap on its own and is tracked as a follow-up.
- **Errors abort.** The route dispatchers now abort any route whose
  handler failed before handling it, so a service error or a body that
  fails to collect ends in a failed request, never a hang. The module
  rustdoc carries the one exception and the header-merge rules.
- **Absolute URIs.** Routers match on `Uri::path`,
  which is the path of an absolute-form URI, so an unmodified axum app
  works; the pattern supplies the origin.

## Prerequisite that surfaced

`route.fulfill()` had never delivered a body: the crate sent the fulfill
parameters nested under a key the driver ignores, and documented the
result as an upstream limitation for thirteen driver versions. The same
audit found `continue_` sending a string `post_data` raw where the
driver reads base64. Both fixed first (`bb5be80`), with the wire
builders in a pure module under mutation testing and the former canary
tests turned into positive ones across all three engines.

## Delivered

- Crate side: feature, module, methods on both objects, integration
  tests (axum app on a made-up origin, method/header/body forwarding,
  `ServeDir` static files, `https://` origin, context scope, cookies
  round-tripping, failing service aborts, WebKit redirects failing fast,
  unmatched requests reach the network, status passthrough), changelog,
  skill section.
- Landing page: a `feature-route-service` card (unreleased until the
  release that carries it ships) linking to a second walkthrough section
  and to the module reference, both built from compile-checked snippets,
  and a site-e2e test that serves the site's own wasm bundle through
  `route_service` on an `https://` origin with its version manifest
  answered by the same axum router, then rewrites that backend's answer
  and takes it down under the running app, writing each step's receipt.
  The walkthrough spends its steps on what a socket-served directory
  cannot show: the backend is a value the test owns.

## Remaining

- Downstream: a consumer whose e2e harness binds an ephemeral port for a
  wasm app can replace that server with `route_service`.
- Follow-ons worth their own passes: a spec-conformance xtask that diffs
  each wire builder's keys against the protocol spec at the pinned tag,
  `fetchResponseUid` support on `FulfillOptions`, and running the CI test
  jobs with `--all-features` so opt-in features are tested too.
